> Personal-use experimental project. The entire implementation and documentation were written with AI assistance / generated by AI for the author's own Slay the Spire 2 setup. It is not presented as a stable community release or supported product.

Local Slay the Spire 2 mod implementing an experimental multiplayer protocol. Configuration sync requires a compatible version on both host and client; a one-sided installation remains inert. Because the mod relies on Harmony patches against game internals, compatibility must be revalidated after game updates.

## Scope

- Reads configuration objects registered with BaseLib.
- Reads setting bindings registered with RitsuLib when RitsuLib is installed.
- Includes only registrations owned by a loaded mod whose manifest declares `affects_gameplay: true`.
- Applies the host snapshot to multiplayer clients in memory only (or logs a dry run).
- Restores the client's original in-memory values when the lobby / run ends.
- Restores before the normal game quit path runs, so BaseLib does not save temporary host values on exit.
- Advertises a minimal capability marker in the game's existing handshake and sends no custom message unless the host advertises the same protocol.
- Uses protocol version, request correlation, payload hashing, size limits, host identity checks, and structured `GCS|...` log events.

The current BaseLib and RitsuLib APIs do not expose per-setting gameplay metadata. The game-level manifest flag is therefore the narrowest authoritative classification available; no name-based guessing is performed.

The synchronizer's own `GameplayConfigSync` settings are explicitly excluded from snapshots. Its BaseLib settings are:

- `Enabled`: master switch.
- `DryRun`: validate and log snapshots without applying values.
- `Diagnostics`: normal or verbose structured logging.
- `FileLogging`: write a dedicated UTF-8 log with 2 MiB size rotation and five archives; enabled by default.
- `AllowUnsafeRitsuBindings`: opt in to RitsuLib bindings whose persistence behavior cannot be proven safe; disabled by default.

RitsuLib currently exposes no general public way to write a value temporarily without persisting it. The default is therefore fail-closed: transient bindings and the known autosave compatibility adapter are accepted; unknown binding implementations are skipped unless the unsafe opt-in is enabled.

`affects_gameplay` is false because this mod contributes no cards, rules, models, or balance settings of its own. Like AutoModSubscriber and Multiplayer Mod Sync, it uses a removable entry in `PeerVersionInfo.otherMods` as a capability sidecar. A client sends the BaseLib custom request only after reading a matching host marker. Therefore a one-sided installation neither performs synchronization nor sends an unrecognized custom message. The third-party settings selected for a snapshot still come exclusively from mods whose manifests declare `affects_gameplay: true`.

## Multiplayer test logs

Search `logs/godot.log` on both peers for `GCS|`. Match the same `request=` value across both logs and verify the event sequence:

1. client `CAPABILITY_OK`, then `REQUEST_SEND`
2. host `SNAPSHOT_CAPTURE` and `SNAPSHOT_SEND`
3. client `SNAPSHOT_APPLY_OK` (or `SNAPSHOT_DRY_RUN`)
4. client `RESTORE_OK` on disconnect or run cleanup

The `sha256=` prefix must match on host and client. Logs include identities and counts, not raw configuration values.

The same events are written to `user://GameplayConfigSync/logs/gameplay-config-sync.log` when `FileLogging=true`. Each line has UTC time, a monotonic sequence number, severity, and an event code. Files rotate at 2 MiB and retain five archives.

For a one-sided test, expect `CAPABILITY_MISSING` and `REQUEST_SKIPPED`, with no `REQUEST_SEND` or snapshot events.

## Repository layout

- `src/` — mod source.
- `GameplayConfigSync.json` — mod manifest; the authoritative source of the version and the game version requirement.
- `GameplayConfigSync.csproj`, `Directory.Build.props` — build project.
- `.github/workflows/` — builds on push, publishes on tag.
- `cliff.toml` — changelog generation config.
- `docs/` — design, safety, research, and test notes.
- `dist/GameplayConfigSync/` — build output; intentionally excluded from Git.

## Build

```
dotnet build -c Release
```

The output lands in `dist/GameplayConfigSync/` as `GameplayConfigSync.dll` and `GameplayConfigSync.json`. Copy that whole folder into the game's `mods/` directory; the result is `mods/GameplayConfigSync/`.

Local builds reference the game assemblies from your own installation, located via `Directory.Build.props`; override with `dotnet build -c Release -p:STS2GameDir="D:/your/path"` when the game lives elsewhere. On machines without the game — including CI — the build automatically falls back to metadata-only reference assemblies from NuGet, so no game installation is required.

Releases are produced by CI: push a `v*` tag and the workflow builds and attaches the artifacts to the corresponding release.
